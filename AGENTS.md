# Development

- This repository contains one independently installable DSH plugin. Keep the plugin manifest, build scripts, and source at the repository root.
- Target DSH releases dsh-v0.2.2-rc.5 and dsh-v0.2.3-alpha.2; verify public contracts against the tagged upstream sources. Never patch the host or inspect its DOM to navigate.
- Use `pnpm dev` for local integration: it builds the plugin, links it into an isolated `workbench-dev` profile cloned from `web`, and boots the web client. Source changes rebuild and hot-reload through DSH client HMR; host-side changes need a restart.
- Use the upstream [DSH UI/UX skill](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.5/.agents/skills/dsh-client-ui-ux/SKILL.md) and theme tokens as the visual foundation. Use shadcn/ui (Radix) controls and scoped portals; no visible native select or custom confirmation overlays. No global Tailwind preflight. Built-in templates may use distinct layouts; custom pages can override style at user request. Check rendered UI in light/dark and constrained widths.
- Workbench uses actual host data; no mock production content. Do not grant generated code host or shell access.
- Development phase: prioritize delivering the agreed requirements and resolving blockers. Keep documentation concise; retain the existing small core unit tests and local build/typecheck commands, but do not require exhaustive testing on every change. Defer GitHub Actions, browser automation, cross-platform build matrices, automated packaging and release pipelines until release preparation or explicit request. Validate the main flow in a real local DSH client once the feature set is ready; explicitly distinguish unverified integration from completed implementation.
